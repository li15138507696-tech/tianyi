# 升仙原著规则与工程适配清单

审计日期：2026-10-26。目标是为天意模组的升仙实现留下一份可以追溯的边界清单。原著步骤、Minecraft 实现参数和未查明事项分开记录；“严格按原著”不允许把数值游戏化冒充成原著定论。

状态标记：

- **已核**：所引章节能支持这一条规则，或本体字节码已经确认该行为。
- **游戏映射**：为了 Minecraft 可玩性而作的实现取舍，必须标为工程参数，不得归于原著。
- **阻塞**：缺少完整原文、依赖能力或行为证据，不能开放对应路线，也不能声称全面还原。

## 可实现范围与禁止声明

当前代码已有纯逻辑状态机、不可变本体修为快照、托管事务状态、恢复 reducer，以及独立 schema 3 Overworld `SavedData` 账本。schema 1 终态历史保留，schema 2 活动会话迁移为空求知账本；无法证明 escrow 关联的活动记录被隔离；未知未来 schema 只读保留。新增的师法自然核心只允许证据白名单主题，按 profile 预算和三气相对容差计算部分完整度，并把序号/知识 grant 与会话 revision 一起 CAS 保存；目前只有“研究力道”主题 ID，没有可展示的知识正文，也没有客户端入口或逐刻窗口服务。登录和重生事件会调用恢复服务，但因无稳定蛊源，服务只报告等待并保留双方记录，不扫描未加载容器、不改物品。旧 `Immortal.Ascension` 仍只是弃用演示模型；玩家操作网络、界面、阶段载体、真实蛊虫转移、仙窍空间和特效未接入，普通路线 profile 仍关闭。

`AscensionProgressionReader` 仅从已存在的本体玩家附件读取 `zhuanshu`、`jieduan`、`renqi`、`shouyuan`、`zhenyuan`、`zuida_zhenyuan` 并校验数值；它不写本体字段，也不代表对这些变量所有消费者和写入路径的审计已完成。当前三个明确门槛仍是：本体六转 rank/真元兼容适配、真实仙窍空间、跨重连且可证明唯一的本命蛊来源。原著特殊路线必须按独立 profile 放行；规则未知时返回明确阻止原因，而不是默认普通路线。

现阶段不得对外称“已完整还原全部原著升仙过程”。完整声明至少要有：章节证据映射、所有承诺 profile 的支持矩阵、可靠死亡/重生处理、蛊虫唯一转移、仙窍与仙元闭环、独立服务器及多人实机记录。
