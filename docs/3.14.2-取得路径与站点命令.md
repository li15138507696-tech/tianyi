## 1. 任务 A：有限资源点的命令入口

3.11 删掉旧 `sites` 子命令时，把新系统的入口一起带走了：管理员只能看世界，没法查、没法收尾、
没法解除单点隔离。3.14.2 补回四个入口，全部 **OP ≥ 2**，全部只动账本与隔离状态。

| 命令 | 作用 | 边界 |
| --- | --- | --- |
| `/tianyi site` / `/tianyi site list` | 列有限资源点：短 id、模板、维度坐标、阶段、剩余实物、守护数量 | 最多 **20** 条，按「维度 → x → y → z」排序；不输出全图、不输出幕后评分 |
| `/tianyi site status <id>` | 阶段、revision、库存各项、槽位物化进度、`SitePlacement.guardianStatus`、最近失败原因 | 只读账本 + 一个**已加载**点的守护兽状态；绝不为了查询去加载世界 |
| `/tianyi site retire <id>` | 安全条件下退役（写进墓碑，同区域不再生成第二处） | 仅 `DEPLETED` / `DESTROYED`，或 `MATERIALIZING && physicalRemaining()==0`；有未完成事务时拒绝 |
| `/tianyi site release <id> --note <理由>` | 解除**单点**隔离 | 必须带 note；复用 `FiniteSiteState.releaseQuarantine` 语义；仍有未完成事务时拒绝 |

### 1.1 `<id>` 怎么打

`site list` 只显示前 8 位。`status/retire/release` 接受**完整 id 或其唯一前缀**（大小写不敏感）。

- 精确匹配优先；
- 前缀只有在**恰好一个**候选时才算命中；
- 歧义（多个候选）与未命中都会明确回话，**不会挑一个动手**——猜错的代价是动错资源点。

解析逻辑在 `resource/SiteCommandArgs`（纯逻辑，离线可测）：`siteId()` / `ambiguous()` / `shortId()`。

### 1.2 retire 复用了什么

- 一般情况：直接 `FiniteSiteState.retire(id)`——它自己就把安全条件、墓碑上限、
  「未提交事务不许消失」三件事判完了。
- 卡死点（`MATERIALIZING` 且剩余实物为 0）：先 `FiniteSite.abandon()` 收尾
  （未物化的**虚拟**库存记为 `destroyed`，与 `retire` 的既有口径一致），再 `retire`。
  回话会明确写出「虚拟库存 N 份记为 destroyed」。
- **不做**的事：不补货、不改阶段语义、不重放任何写入、不回滚已经发生的采集。
- `retire` 之后帐上的点进墓碑（`tombstones`），记号保留，同一区域不再刷第二处。

### 1.3 release 复用了什么

`FiniteSiteState.releaseQuarantine(id)`：先确认没有未提交事务，再让
`FiniteSite.releaseQuarantine()` 回到**账本能证明的那一档**（还在待物化 → `MATERIALIZING`；
还有实物 → `ACTIVE`；否则 `DORMANT` / `DEPLETED`）。

note 只会出现在两处：本次命令回话 + 服务端日志 `[天意·资源点] 解除隔离 ...`。
**账本 schema 不变**（没有给站点加 note 字段）。

## 2. 任务 B：宿命蛊的取得路径

### 2.1 一句话

> 站在一处**流派地形上的守护资源地**，亲手打死它的**守护兽**，交够**三种真实材料**，
> 输入 `/tianyi seek suminggu`，宿命蛊会以**掉落物**的形式落在那个容器上方。

入口只有这一个：`/tianyi seek suminggu`（**不设权限门槛**，普通玩家可执行）。

### 2.2 为什么是命令而不是右键

- 世界层**禁止给玩家发聊天消息**（既有审计硬约束：`world/` 不许 `displayClientMessage` /
  `sendSystemMessage`）。而这条路径必须能说清「还差什么」。命令层回话是既有约定。
- 右键容器会和「开桶取蛊材」抢同一个交互；改一个方块交互又要动 `SiteProtection` 的边界。
- 命令入口让「前置判定」变成可离线单测的纯函数，而不是只能进游戏才知道对不对。

命令入口**不是**「输入即得」：所有前置都在服务端重新取事实并判定（见 2.3），
且**同一地点同一人只成功一次**（见 2.5）。

### 2.3 前置条件（顺序固定，先说的就是最该补的）
判定在 `DestinySeek.firstReject(Facts)`，顺序即优先级：

| # | 前置 | 取证方式（全部复用既有系统） | 失败原因（回话原文口径） |
| --- | --- | --- | --- |
| 1 | 执行者是玩家 | `CommandSourceStack.getPlayer()` | 必须由在场的玩家执行 |
| 2 | 24 格内有已物化的守护资源地 | 账本 `FiniteSiteState.sites()` + `SitePlacement.clue()`（容器记号/类型/指纹必须仍属于该点）；取最近一处，同距按站点 UUID 定序 | 附近没有已物化的守护资源地 |
| 3 | 该点是 `FiniteSite.Kind.GUARDED` | `site.kind()` | 这个资源点不是守护资源地 |
| 4 | 所在地形是**流派地形** | `SiteTerrain.hasTerrainGuardian(biome)`（雷泽 / 碎金丘陵 / 赤焰烬土 / 万仞千山） | 不在四道流派地形上 |
| 5 | 守护兽与地形映射一致 | `DestinySeek.terrainGuardianMatches()` ↔ `SiteTerrain.GUARDIAN_BY_BIOME` | 守护兽与地形映射不符 |
| 6 | 该点绑着守护兽 UUID | `site.guardians()` 非空 | 该点没有绑定守护兽 |
| 7 | **本人亲手**打死过它 | `DestinySeekState.killerOf(siteId)`，由 `LivingDeathEvent` 只认「UUID 匹配本站守护兽 + `getSource().getEntity()` 是玩家」写入 | 还没有击败这个点的守护兽 |
| 8 | 材料够 | `DestinySeek.materialsComplete()`（背包逐格数，只读） | 材料不足：还差：…… |
| 9 | 宿命账本可写 | `DestinyCustodyState.mutationReady()` 且未隔离 | 账本当前不可写 / 隔离中 |
| 10 | 账本上没有正品 | `custody().exists()` | 全存档只能有一只 |
| 11 | 幂等键没用过 | `DestinySeekState.claimed(DestinySeek.key(siteId, playerUuid))` | 这次取得已经成功过一次 |

关于第 4 条要说清楚：**守护资源地本身不设地形门槛**（`SiteTerrain.GUARDED_BIOMES` 为空，
这条是 `SiteTerrainTest` 里登记过的既有设计：`if (GUARDED_BIOMES.isEmpty())` 否则「群系没生成
就永不出现」）。所以取得路径把「流派地形」作为**自己的**额外门槛：
只有在四道有守护兽映射的地形上，这条路径才成立；原版群系上的守护地可以照常采蛊材，但取不到宿命蛊。

关于第 2 条还要说清楚：**这个点必须还在账本上**。守护资源地的桶一旦被抽空（或被破坏、被替换），
对账会把该点判成 `DEPLETED` / `DESTROYED` 并很快退役成墓碑，`SitePlacement.clue()` 也就不再认它。
也就是说：

> 这一刀打完、仪式做完，再去把桶里的蛊材掏空——顺序不能反。
> 反过来也不至于卡死：别的流派地形上的守护地会继续生成，换一处照同样流程即可
> （击杀记录是**按站点**记的，不是按玩家记的）。

这是**有意**的紧口径：宁可要求「桶还活着」，也不给「站在空地板上凭空取一只世界唯一的蛊」开口子。
如果实机反馈觉得太苛刻，改动点也只有一处（`nearestGuardedSite` 的过滤条件），不要动判定顺序。

### 2.4 材料与数量（**平衡参数**）
| 物品 id | 中文名 | 数量 | 来源（本体既有） |
| --- | --- | --- | --- |
| `guzhenren:gu_caidanxincao` | 蛊材·丹心草 | **3** | 守护资源地的桶里（一处 4–8 份） |
| `guzhenren:gucaileimingcao` | 蛊材·雷鸣草 | **3** | 守护资源地的桶里（一处 4–8 份） |
| `guzhenren:gucaiyuanshi` | 元石 | **6** | 元石露头（一处 3–6 颗） |

调价只改 `DestinySeek.COSTS` 一处——判定、缺口文案、命令回话、审计全部读同一张表
（`materialsComplete()` 与 `shortfall()` 同源，测试里锁了这条）。

扣除方式：`inventory.setItem(slot, ItemStack.EMPTY)`（整格清空）与 `stack.shrink(take)`（同格减少）。
**不发放任何东西**；创造模式**也照扣**（宿命蛊没有创造豁免，没有后门）。

### 2.5 交付方式与防重复发放

交付：`DestinyCustodyService.materializeAt(...)` 把载体做成 `ItemEntity`，
落在该点**容器上方**（站点坐标 +1 格）。拾取才进背包——**命令层不写任何玩家背包**。

顺序（写在代码注释里，也在审计里正向断言）：

1. 判定 → 2. **实体化**（`DestinyCustodyService.materializeAt` → 内部 `DestinyCustody.issue`）
→ 3. 扣材料 → 4. 记幂等键 → 5. 写见闻录 + 既有同步。

为什么实体化在前：它是唯一不可重复的原子动作，账本说「已经有正品」时会在**扣材料之前**就拒绝，
所以不会出现「扣了材料却没给蛊」。

三道防重复：

| 层 | 机制 | 挡住什么 |
| --- | --- | --- |
| 账本 | `DestinyCustodyService` 的 `ALREADY_EXISTS` / 隔离 / 存档不可写 | 第二次实体化（不管是谁、从哪触发） |
| 幂等键 | `DestinySeek.key(siteId, playerUuid)` 记进 `DestinySeekState`（新存档键 `tianyi_destiny_seek`） | 同一地点同一人重复领取（即使正品之后丢失/待核验） |
| 现场 | 每次都要重新取事实（点是否还在、容器是否仍属于该点、守护兽击杀记录、材料） | 换人刷、换点刷、重复点击 |

重启/重连安全：击杀记录、幂等键都在 SavedData 里（`setDirty()` 之后由存档调度落盘），
不靠任何内存状态。

回溯也是自洽的：`SnapshotService.SUBDIRS` 含 `data`，所以 `tianyi_destiny_seek.dat`
与宿命保管账本一起被回退——「回溯到取得之前」等价于「这次取得没发生过」（连蛊也没了），
不是刷取手段。回溯本身的边界（玩家已知信息、背包不随回溯转移）仍按既有口径，本版未改。

### 2.6 成功时给的见闻录条目

一条，走既有 `JournalStore.noteDestinySeek(...)` → `JournalStore.note(player, entry)`，
再由命令路径调一次既有 `JournalNet.sync(player)`。

- **不加 payload、不改协议、不加字段**；
- `Kind.SIGHT` / `Source.WITNESSED`，位置是**玩家自己站的地方**，标题只写「取得宿命蛊」；
- 每个 12 000 刻窗口 + 站点 id 一个 key，不重复堆条目。

### 2.7 刻意不做的事

- 不做「输入玩家名改命运」，不做「点击即得」；
- 不加任何跳过前置的调试后门（管理员想要一只，仍然走 `custody recover`）；
- 不给守护兽击杀奖励、不补生守护兽、不扫世界、不强制加载区块；
- 不改阶段语义：这条路径**只实体化**，绝不推进 `Destiny.Stage`。

## 3. 失败对照表（玩家会看到什么）

| 情况 | 回话（要点） |
| --- | --- |
| 不在守护地 24 格内 | 附近没有已物化的守护资源地……需在 24 格内，且容器确实属于该点 |
| 点在原版群系上 | 不在四道流派地形上（雷泽 / 碎金丘陵 / 赤焰烬土 / 万仞千山） |
| 守护兽还活着 / 不是你打死的 | 还没有击败这个点的守护兽（只认这一只、被你亲手打死的那次死亡事件） |
| 兽是被环境或别的生物打死的 | 同上（`getSource().getEntity()` 不是玩家 ⇒ 不记） |
| 材料不够 | 材料不足：还差：丹心草 ×2、元石 ×6 |
| 账本已有正品 | 全存档只能有一只，不会再出现第二只 |
| 账本隔离中 | 先处理账本（`custody release <serial> <note>`） |
| 已经领过 | 这次取得已经成功过一次（同一地点同一人只发放一次） |

## 4. 未实机边界（**必读**）

离线能证明的：

- 编译通过（108 源，`javac exit 0`）；
- `DestinySeekTest` 94 项：价目 / 缺口文案 / 同源一致性 / 幂等键 / 前置判定顺序 / 地形映射 /
  note 校验 / 站点 id 前缀解析 / 模板与候选守护兽；
- 静态审计（新增断言，不替换旧的）：取得路径只有一个实体化入口、不自造实物、真扣材料、
  不写玩家背包、世界层不播报、小账本只记事实、命令入口不挂 OP、`retire/release` 不物化。

**没有实机验证**（只能在游戏里看，任何静态审计都证明不了）：

1. 真实群系里 `guzhenren:leize` 等四道流派地形是否真的生成、`SiteTerrain.biomeId` 是否拿到 key；
2. 真实守护兽生成、AI、死亡事件与 `getSource().getEntity()` 是否确实是玩家
   （例如火焰熊的间接伤害，凶手是否被判成玩家）；
3. `BarrelBlockEntity` 的记号与指纹是否稳定（容器被替换/被漏斗抽空会让"现场取证"失败）；
4. 背包扣除的真实手感（多格分散时的 `shrink`／置空）、服务端与客户端物品栏同步；
5. 掉落物在该点容器上方的落点是否被方块挡住、是否被漏斗/其他玩家捡走；
6. 重启后 `tianyi_destiny_seek` 的实际落盘时点（`setDirty` 不等于同步写盘）；
7. `/tianyi site release <id> --note …` 这种「字面量 `--note`」在真实客户端补全里的表现；
8. 「先把桶掏空再想做仪式」这一条时序：对账把它判成 `DEPLETED` 再到退役成墓碑之间有多少刻，
   离线只能从 `SiteBudget.CHECK_INTERVAL_TICKS = 200` 推，真实间隔没测过。
