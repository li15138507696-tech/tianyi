# 升仙会话与本命蛊托管设计

日期：2026-10-28

状态：用户已审阅通过；首阶段实现与源码验证完成，升仙入口仍保持关闭

范围：天意模组升仙服务端数据与物品托管

## 目标

为后续升仙入口准备可恢复的服务端会话与本命蛊托管层。会话进度由世界存档记录，物品只能从服务端核实的真实槽位进入托管；崩溃恢复时发现证据不一致就保留证据并隔离，不自动复制、退款、消耗或重置升仙进度。

本阶段不开放六转写入、不创建仙窍维度、不加入客户端入口。普通路线只有在本体修为适配、真实仙窍空间和本命蛊托管能力全部可用后才允许开始。

## 依据与边界

- 固定本体 JAR 的直接字节码扫描记录了境界 `zhuanshu` 155 个写入类、阶段 `jieduan` 55 个、真元 `zhenyuan` 1849 个、真元上限 `zuida_zhenyuan` 68 个、人气 `renqi` 3 个、寿元 `shouyuan` 34 个。境界写入包含培养界面、命令、死亡处理和实体效果；真元上限还会参与本体空窍显示编码。
- 扫描覆盖直接 `GETFIELD` / `PUTFIELD`，不覆盖反射、间接调用或实机运行行为。不能据此宣称本体支持六转或仙元切换。
- `BenMingGu1Procedure` 读取本体实际物品槽并把栈复制进 `PlayerVariables.BenMingGu`；该缓存副本不是物品身份或托管凭证。
- `AscensionMachine` 已定义阶段迁移，`AscensionStore` 已用 revision 比较更新 `Session`，但尚无游戏动作写入会话，也没有真实物品托管。
- 玩家存档、世界 `SavedData` 和其他容器不共享原子提交。设计不承诺硬崩溃下恰好一次；含糊状态必须隔离，不能自动奖惩。

## 结构

### 服务端事实快照

新增只读适配层，仅接受在线 `ServerPlayer`，从本体变量读取并校验 `zhuanshu`、`jieduan`、`renqi`、`shouyuan`、`zhenyuan` 和 `zuida_zhenyuan`。快照保留本体原值与采样时间，不把它们换算成原著单位，不写回本体字段。数值缺失、非有限或玩家数据尚未就绪时返回明确阻止原因。

客户端不得提交这些事实、物品 ID、物品栈或成功结果。会话开始条件由服务端重新核验；当前缺少能力时不得创建 `PREPARING` 会话。

### 会话与托管存档

扩展现有 `AscensionStore`，让会话和托管记录共用同一份世界 `SavedData`。会话继续使用现有 revision 比较替换；每条托管记录包含服务端生成的托管 ID、主人 UUID、会话 UUID、稳定来源槽位引用、完整物品栈数据、状态和 revision。`Session.guEscrowId` 指向对应记录。

物品在会话创建时进入托管，之后会话只引用同一 escrow ID；这样玩家不能在碎窍后替换或丢失本命蛊。托管状态采用有限迁移：

`PREPARED → SOURCE_REMOVAL_PENDING → HELD → DISPOSITION_PENDING → RESTORED / COMMITTED`

任何重放、所有者不符、多个可见副本、未知槽位或无法解码的数据进入 `QUARANTINED`。托管 ID 只用于关联记录；它本身不证明物品唯一。副本检查必须覆盖获准的来源与所有已知使用路径；若有未受控的复制或转移路径，`UNIQUE_GU_ESCROW` 保持关闭。物品结局（归还、提交或消耗）必须由已启用的路线规则明确声明，未知规则不得自动选择。

### 恢复与兼容

- 升级存档时将 schema 1 中可解码的会话迁移到新 schema，逐条保留原会话 ID、revision、阶段、结果和隔离记录。
- schema 1 中没有托管 ID 的非终态会话保留原始记录并隔离，不允许恢复或继续推进；终态会话保留作历史记录。
- 未知未来 schema 整体保持只读并原样保留；损坏或冲突的会话/托管记录逐条隔离。
- 玩家重连或世界重新加载后，服务端按托管状态、来源槽位和会话 revision 核对。来源槽位未加载时暂缓操作；证据不唯一时隔离，不自动补物品或清除记录。
- `PREPARED` 或 `SOURCE_REMOVAL_PENDING` 阶段若原槽位仍有与快照完全相同的物品且会话尚未碎窍，可取消未完成的托管准备并让物品留在原槽位；`SOURCE_REMOVAL_PENDING` 阶段若原槽为空、记录完整且未发现副本，可转为 `HELD`。`PREPARED` 阶段物品缺失、槽位内容改变、会话已碎窍或出现多个可见副本时隔离，因为世界存档与玩家存档之间无法确认唯一提交顺序。
- `HELD` 阶段原槽位应为空。若物品在未经账本记录的状态下重新出现，保留物品和托管记录并隔离；不自动删除或再发一份。
- 碎窍提交位仍由会话账本保存。死亡、重生和克隆只恢复可核实的玩家显示状态，不把已碎空窍恢复成未开始。

## 主要流程

1. 服务端读取并校验玩家修为快照、空窍证据和真实本命蛊来源；托管只接受数量为 1、可保存且可稳定重定位的真实物品栈。
2. 校验路线 profile 及三项能力声明。任一能力未实现时返回具体阻止项，不创建会话、不移除物品。
3. 在同一 `SavedData` 更新中创建 `PREPARING` 会话和 `PREPARED` 托管记录，并互相写入 ID。之后核对来源槽位未变化、推进为 `SOURCE_REMOVAL_PENDING`、移除真实物品并确认 `HELD`。只有 escrow 为 `HELD` 时才允许开始碎窍；同一会话的重试必须命中原事务，不能新建第二份托管物。
4. 碎窍等不可逆会话迁移通过 `AscensionStore.compareAndSet` 核对 revision。`PLACE_GU` 仅在三气和托管记录都由服务端确认后推进状态。
5. 成功或失败后的蛊虫处理由 profile 明确决定。处理完成前保留 `DISPOSITION_PENDING`；无法恢复时进入隔离。

实际来源槽位若无法跨断线稳定标识，或该槽位不能由服务端独占核验，则托管能力维持关闭。不得用 `PlayerVariables.BenMingGu` 的副本代替真实物品。

## 验收条件

- schema 1 迁移保留所有可解码会话；未来 schema 不被覆盖。
- 会话和托管记录持久化后可按 ID 重载，重复事务及过期 revision 被拒绝。
- 恢复时来源物缺失、来源仍在、出现多个可见副本、槽位未知和 NBT 损坏分别进入明确的安全分支；不自动生成第二只蛊。
- 死亡或重生不清除独立会话账本，也不自动撤销已提交碎窍。
- 本体修为适配、仙窍空间或物品托管任一未就绪时，普通路线仍不可开始。
- 文档与界面不得宣称六转兼容、硬崩溃恰好一次或尚未实现的仙窍空间。

## 未决实现前提

1. 需要继续核实本体菜单槽 0 的稳定身份及其与玩家持久库存的关系；如果断线后无法重新定位，首版只接受可稳定核验的服务端库存槽。
2. 需要实现真实仙窍空间和明确的空窍主人/入口规则。
3. 需要逐类审计 rank 与仙元消费者，给出本体修为兼容适配；在此之前只读快照，不写六转状态。
4. 需要为每个启用 profile 补齐蛊虫成功与失败后的归属规则；未知路线保持关闭。
