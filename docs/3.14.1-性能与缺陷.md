## 2. 每 tick 路径量化（20 次/秒）

入口链：`TianyiEvents.onServerTick`（`TianyiEvents.java:34`）→ 4 个转发。

| # | 路径 | 频率 | 每次实际做的事 | 依据 |
|---|---|---|---|---|
| 1 | `WillServer.onServerTick` | 20/s | `counter++`；`server.overworld().getGameTime()`；2 次档位配置读（`force()` + `pressureOn()` 各读一次 `INTENSITY`）；`IntelState.get(server)`（**每 tick 分配一个 `SavedData.Factory`**）；`intel.onTick` → `plans.due(now)` | `WillServer.java:68-106` |
| 2 | `EncounterService.tick` | 20/s 进入，1/s 干活 | `++tick % 20 != 0` 直接返回；每 20 刻遍历一次在线玩家（O(玩家)） | `EncounterService.java:81-128` |
| 3 | `FiniteSiteService.tick` | 20/s 进入 | `SiteSettings.active()`（配置读，默认 false 直接返回）+ `SiteBudget.due(gameTime)`（模 200） | `FiniteSiteService.java:82-86` |

`getBlockEntity()`。`audit_perf.py` 把这条写成了断言，防止后人加回来。

`ActionLedger.due(now)` 是 tick 路径上唯一"扫账本"的地方：账本上限 `MAX_PLANS = 256`，
最坏 256 次 `p.open(now)` + 一次排序。3.14.1 起账本为空时直接返回 `List.of()`（§4.6）。

**最大单次尖峰**：一次 `SiteProtection.check`（球壳扫描）在**同一个 tick 里**要跑完
274625 次位置访问。`SiteBudget.CANDIDATES_PER_CHECK = 4` 意味着最坏情况下一个 tick 里
可能出现 4 次这样的扫描（生成阶段每轮最多 4 个候选）。这是 3.14.0 里唯一可能造成
**单 tick 十几毫秒级卡顿**的地方，也是本次改动的重点。真实毫秒数**未测**（需要 spark）。

## 4. 优化前后对照

性质说明：下面 7 处都是**可证明等价**的改动——调用次数、返回结果、世界副作用都不变，
只去掉重复工作与临时对象。**没有删除或放宽任何节流**（200 刻对账、10 刻见闻录同步、
决策周期、`ACTIVE_JOBS_PER_TICK`、`CANDIDATES_PER_CHECK` 全部原样）。

### 4.1 `SitePlacement.matchesOwned`：球壳里每位置 × 每槽位 new 一个 BlockPos（已修）

| | 改动前 | 改动后 |
|---|---|---|
| 实现 | `site.slots().stream().filter(s -> pos(s).equals(p)).findFirst()` | 单层 `for` + `s.x()==p.getX() && ...` |
| 每次调用分配 | 每槽位 1 个 `BlockPos` + 1 条 Stream 管线 | 0 |
| 单次球壳扫描（估算） | 1.3×10⁵ 位置 × 槽位数（植物可达 8，守护兽 1）≈ **1.0×10⁶ 个临时 BlockPos** | 0 |
| `hasChunkAt` | 每个位置都调用 | 只对**确实命中槽位**的位置调用（≤ 槽位数） |

等价性：`pos(s).equals(p)` 就是 `x/y/z` 三项相等；`hasChunkAt` 无副作用，挪到命中之后
不改变任何分支结果（未加载时两者都返回 false）。
位置：`SitePlacement.java:401-413`。

### 4.2 `SiteProtection.benignBlockEntity`：球内每个自然方块都查一次方块实体（已修）

| | 改动前 | 改动后 |
|---|---|---|
| 每个自然方块 | `level.getBlockEntity(p)` → `getChunkAt` + 方块实体表查询 | 先判 `state.getBlock() instanceof EntityBlock`，不是就直接 `return true` |
| 单次扫描（估算） | 约 1.3×10⁵ 次 `getBlockEntity` | 只剩真正可能是方块实体的位置（泥土/石头/草方块/原木/树叶全部跳过） |

等价性：`Level.getBlockEntity(pos)` 内部就是 `getChunkAt(pos).getBlockEntity(pos, IMMEDIATE)`，而
`LevelChunk` 的实现在「该位置没有登记记录 **且** 方块不是 `EntityBlock`」时返回 `null`；
本方法对 `null` 的答案就是 `true`。所以对非 `EntityBlock` 的方块，改动前后的返回值必然相同。
（唯一理论差别：某个位置残留了「方块已被替换成非 `EntityBlock`、但方块实体表里还有旧记录」的
不一致状态。`setBlockState` 会清掉对应记录，正常玩法下不会出现。）
位置：`SiteProtection.java:162-169`。
> ⚠️ 唯一需要编译期确认的新 API：`net.minecraft.world.level.block.EntityBlock`。
> 同包的 `BarrelBlock` 已被本工程引用（`SitePlacement.java:454`），因此该包与
> 「方块实体靠 `EntityBlock` 提供」的模型是确定的；若编译报错，只需回退这 3 行。

### 4.3 `Observation.field`：每个玩家每次画像 28 次 `Class.getField`（已修）

| | 改动前 | 改动后 |
|---|---|---|
| 每次 `probe` | 28 次 `PlayerVariables.class.getField(name)`（搜索 + 拷贝 `Field` 对象），字段名写错时还要每次抛/接异常 | 28 次 `Map.get`；首次解析后缓存 `Field` |
| 调用频率 | 决策轮每个在线玩家 1 次；每条灾劫/布局各 1 次 | 同左，但反射查找只发生一次 |

同时把「字段名不存在 → 静默按 0」改成**按名字告警一次**（见缺陷 D4）。
位置：`Observation.java:61-70, 223-249`。

### 4.4 `EncounterService`：每个在线玩家每秒一包（已修，且**不改可见行为**）

先纠正一个容易想当然的地方：这份包**不是**纯粹的浪费，客户端会拿它做本地倒计时外推：

```java
// JournalClientState.java:40-43
secondsLeft() - (System.currentTimeMillis() - encounterReceivedAt) / 1000
```

所以「少发一个内容相同的包」会不会让玩家看到不一样的秒数，取决于**这些秒数有没有被画出来**。
逐相位核对（`JournalScreen.java:481-482, 503-506` 只画 FIGHT 与 WON/LOST/FINISHED）：

| 相位 | 服务端 `remainingTicks` 每秒变化？ | 客户端是否显示秒数 | 去重会不会改变可见行为 |
|---|---|---|---|
| WAITING | 会（`EncounterRun.elapse` 递减） | 不显示 | 包内容本来就变，照发 |
| SEEK / READY | **不会**（`elapse` 只对 WAITING/FIGHT/终态递减） | **不显示** | 会抑制，但玩家看不到任何差别 |
| FIGHT | 会 | 显示 | 包内容本来就变，照发 |
| WON/LOST/FINISHED | 会递减到 0 为止 | 显示 | 减到 0 之后才可能被抑制；此时本地外推 `max(0, 0-Δ)=0`，与改动前一致 |

结论：只在「客户端分辨不出来」的情况下少发。实现与顺序：

| | 改动前 | 改动后 |
|---|---|---|
| `tick` 里的收尾 | `state.setDirty(); sync(p);` ——**无条件** | `state.setDirty(); syncIfChanged(p);` |
| 包的构造 | 每秒构造并发送一次（codec 编码 + 网络写） | 先构造（与发送时一模一样），与上次发的**记录值相等**就不发 |
| 收益（估算） | 每个在线玩家 1 包/秒，包含 SEEK/READY 这种长期冻结的状态 | SEEK/READY、终态冷却归零后、以及死亡/非生存模式玩家不再收重复包 |

等价性：`EncounterSyncPayload` 是 record，`equals` 逐字段比较；客户端 handler
（`JournalClientHandler.java:20-22` → `JournalClientState.acceptEncounter`，`encounter = payload`）
是**整份替换**这份状态，内容不同的包才有意义。
显式路径（登录 / 重生 / 切维度 / 动作回执 / 失败结算 / `tryOpen`）仍然走 `sync`，**一定发**，
并且会把「刚发出去的那一份」也记进去重表——所以重连后紧接的那次轮询对比的是客户端
**刚刚收到**的内容，不会因为旧记录而误判成「不用发」；`logout` 时还会清掉这个玩家的记录。
位置：`EncounterService.java:50-61, 319-325, 380-418`。
`state.setDirty()` 仍然每秒调用（未改），因为 `elapse(20)` 真的会改 `remainingTicks`。

> 若将来把客户端改成「不再本地外推」或「在 SEEK/READY 也显示秒数」，这条去重必须重新评估。

### 4.5 `JournalNet.tick`：每 tick 一次 `Set.copyOf`（已修）

`PENDING` 绝大多数时刻为空，但 `Set.copyOf(PENDING)` 每次都会新建一个集合。
3.14.1 起先判空再拷贝：空集直接返回，非空行为完全不变。
位置：`JournalNet.java:41-49`。

### 4.6 `ActionLedger.due`：每 tick 一个空 ArrayList + 空排序（已修）

账本为空时（绝大多数时间）直接返回 `List.of()`。非空路径的过滤与排序一字未动。
唯一能观察到差别的地方：空结果现在是**不可变**列表——本仓库里 `due()` 只有
`IntelState.java:138` 一个调用方，只做 `isEmpty()` 与 `for` 遍历；测试套件也不改这个返回值。
位置：`ActionLedger.java:68-84`。

### 4.7 `SiteEvidence`：每次写见闻都现算全体 key 总数（已修）

| | 改动前 | 改动后 |
|---|---|---|
| `remember` | `WRITTEN.values().stream().mapToInt(Set::size).sum()` —— O(玩家数 × key 数) | 一个 `int writtenKeys` 滚动计数，`add` 成功 +1、`clear` 归零 |
| `arrived` / `guardianSeen` | 先做现场扫描（读方块/方块实体），再在 `emit` 里查 `WRITTEN` | 先查 `WRITTEN`，已写过就直接返回 |

等价性：计数恒等于「所有集合大小之和」（只在 `add` 返回 true 时 +1，只在 `clear` 时归零，
没有别的增减路径）；`arrived/guardianSeen` 的 key 与 `emit` 内部算出来的完全同一个
（`SiteNotice.key(siteId, event, revision)`），所以提前返回与 `emit` 里返回 false 等价。
位置：`SiteEvidence.java:40-89, 137-151`。

## 6. 残余风险

1. **球壳扫描的量级没变**。本次只把"每个位置的白做"去掉（`getBlockEntity` 与百万级临时对象），
   `274625` 次位置访问与 `getBlockState` 仍然存在。真正的根治是**按需扫描**（只在槽位附近
   而不是 32 格全球壳），但那会改变"周围 32 格不能有玩家建筑"这条保护语义，必须产品确认。
2. **一个 tick 里可能出现 4 次球壳扫描**（`CANDIDATES_PER_CHECK = 4`）。本次没有改这个常数
   （会改变生成概率）。如果实机 spark 显示生成轮有尖峰，第一优先是把 `materialize` 的
   球壳检查改成"跨 tick 分摊"（例如每 tick 只走 1/4 个扇区），而不是调小半径。
3. **`EntityBlock` 是本次唯一新增的 MC API 引用**，见 §4.2 的警告。
4. **`EncounterSyncPayload` 去重依赖两条客户端事实**：(a) handler 是整份替换
   （`JournalClientState.acceptEncounter`）；(b) 秒数只在 FIGHT / WON / LOST / FINISHED 被显示，
   而这四个相位服务端每秒都在递减 `remainingTicks`，所以包内容本来就在变、照发。
   一旦有人把客户端改成增量合并、或在 SEEK/READY 也显示倒计时，这条去重就会漏更新
   （客户端会从冻结的基准继续本地外推）。那时必须给 payload 加序号或改回无条件发送。
5. **`WorldSites.PRODUCE_PERIOD` 与 200 的整除关系**是隐性契约（N6）。审计脚本没有锁它
   （`PRODUCE_PERIOD` 不在纯逻辑包里），仅在此记录。
6. **未实机**：天气、落雷、粒子、容器、守护兽、区块加载、网络包体积、重连后的客户端状态
   全部没有在游戏里看过。离线能证明的只有「调用结构」与「纯逻辑等价」。

## 8. 实机验证清单（进游戏才看得见）

1. 打开有限资源点（`tianyi-sites-server.toml` 里 `enabled` + 对应 kind/模板开关），
