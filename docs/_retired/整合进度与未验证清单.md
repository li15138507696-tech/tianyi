## 〇、17:04 与 17:09 两次「启动即死」的真凶：`options.txt` 里重复的按键行

### 现象

两份报告**都没有 `crash-*.txt`**，`latest.log` 只有 2.5 KB，最后一行永远停在
`Loading ImmediateWindowProvider fmlearlywindow`，随后：

```
Exception in thread "main" java.lang.IllegalStateException:
  Duplicate key key_key.daotu.view (attempted merging values key.keyboard.h and key.keyboard.v)
  at Collectors.duplicateKeyException
  at fml_earlydisplay/DisplayWindow.initialize(DisplayWindow.java:139)
  at fml_loader/ImmediateWindowHandler.load
  at ModDirTransformerDiscoverer.earlyInitialization
```

### 关键证据链

1. 17:04 那次：`mods/` 里确实有 `daotu-1.5.2.jar`（旧独立附属），与合并版共用 `key.daotu.view`；
2. 17:09 那次：**旧 jar 已经从 `mods/` 移除**（重扫 109 个 jar，无任何 `daotu`/`tianfu`/`shenshang`），
   合并版 1.0.13 的按键也已改名成 `key.tianyi.path_view` —— **jar 里根本不存在 `key.daotu.view` 了**，
   但**同一个错一字不差地又出现了**。

那就说明：重复的键**不在 jar 里，而在实例的 `options.txt` 里**。

```
D:\game\mcmod\蛊2\.minecraft\versions\转生到蛊界就要拿出真本事\options.txt

key_key.daotu.view:key.keyboard.h
key_key.daotu.view:key.keyboard.v      ← 同一个按键被写了两次
```

### 为什么自己好不了（死循环）

FML 的 `DisplayWindow.initialize` 在**开窗之前**就读 `options.txt`，用
`Collectors.toMap` 建按键表 —— 同一个 key 出现两次直接抛异常。
也就是说游戏**死在「能重写 options.txt」之前**，所以这份坏文件会一直留着，
每次启动都必然崩在同一行。这正是「删了 jar 也没用」的原因。

H 与 V 的来源：合并前旧附属默认 V、合并版里被设成 H（或反之），
两个 jar 同时在场时游戏分别写了一次，随后提前崩溃没机会去重。

### 处置

- `options.txt` 已修复（脚本 `_pack/fix_options_dup.py`）：
  备份 → 删掉两行 `key_key.daotu.view` → 全文件 `key_key.*` 去重（保留最后一次）→ 回读校验。
  结果：**292 行 / 141 个按键 / 0 重复 / 无 daotu 残留**；
  备份文件 `options.txt.bak-20261024-171027`（11,797 字节）就在同目录。
- `mods/daotu-1.5.2.jar` 已移到 `mods-disabled-旧附属/`（mods 目录已无旧附属）。
- 1.0.13 把按键 id 全部搬到 `key.tianyi.*` —— 这一条是**防复发**：
  即使日后旧 jar 又被扔回来，也不会再产生同名按键行。

### 教训（写进纪律）

| 症状 | 不要看 | 要看 |
|---|---|---|
| 无 `crash-*.txt`、`latest.log` 只有几百字节、停在 `fmlearlywindow` | 最后一个 mod 的名字 | **`options.txt` 里 `key_key.*` 是否重复** |
| 同 id 报错但 jar 里搜不到 | 「是不是没删干净 jar」 | 「存档/配置里是不是留了脏数据」 |

FML 在**开窗之前**读的文件（`options.txt`）一旦损坏，靠改 jar 是修不好的。

## 〇之一、1.0.11 的改动（相对 1.0.10）：新建服务端配置 NPE


### 进展

1.0.10 已经能过 mixin 与 payload 两道关：客户端进得了主菜单，**并且已经开始创建世界**
（日志走到 `IntegratedServer.initServer` → `ServerLifecycleHooks.handleServerAboutToStart`）。

### 现象（`错误报告-2026-10-24_16.43.12.zip`）

```
Description: Exception in server tick loop
NullPointerException
  at java.util.ImmutableCollections$ListN.indexOf
  at java.util.ImmutableCollections$AbstractImmutableList.contains
  at net.neoforged.neoforge.common.ModConfigSpec$ValueSpec.test(ModConfigSpec.java:1120)
  at net.neoforged.neoforge.common.ModConfigSpec.correct(ModConfigSpec.java:246)
  at net.neoforged.fml.config.ConfigTracker.createDefaultConfig(ConfigTracker.java:224)
  at net.neoforged.neoforge.config.ConfigTracker.loadConfigs → ServerLifecycleHooks.handleServerAboutToStart
```

`createDefaultConfig` = **正在新建一个还不存在的配置文件**；`config/` 下确实一个 tianyi 配置文件都没有。

### 根因

我给 AI 配置用了 `defineInList("mode", "auto", List.of(...))`。
NeoForge 21.1.259 的 `ModConfigSpec.correct()` 在新建配置时会对**尚未写入的键**调用
`ValueSpec.test(null)`，而 `defineInList` 的实现是 `acceptableValues.contains(value)`，
`List.of(...)` 对 `null` 直接抛 NPE —— 于是「第一次生成配置」就崩在 tick loop 里。
（DEBUG 日志里能看到它登记的名字是 `tianyi-server.toml`，比文档写的 `tianyi-ai-server.toml` 短，
这也是同一处疏漏：`registerConfig` 用的是两参重载。）

### 修法（三处）

1. **不用 `defineInList`**：改成 `define("mode", "auto")` + `TianyiAiConfig.mode()`
   归一化（小写/去空白/不认识就当 `auto`），三个调用点全改成 `mode()`。
2. **不用 `defineList`**：`allowedHosts` 与 `rewardByDifficulty` 改成**逗号分隔字符串**，
   代码里切分（`allowedHosts()` / `rewardTable()`），坏值跳过并回退内置默认。
   —— 同一类「数组规格在 null 上行为不保证」的坑，一次排干净。
3. **配置文件名显式指定**：`registerConfig(SERVER, SPEC, "tianyi-ai-server.toml")`，
   与文档一致（之前默认生成 `tianyi-server.toml`）。

另外把一份**已填充**的 `config/tianyi-ai-server.toml` 预先放进整合包，
让首次启动直接读已存在文件，连 `createDefaultConfig` 这条路都不走（双保险）。

### 新增审计（`audit_ai.py`）

- 禁止 `defineInList` / `defineList`（附原因）；
- 必须有 `mode()` 归一化入口，且除配置类之外不得直接 `MODE.get()`；
- `registerConfig` 必须显式指定 `tianyi-ai-server.toml`。

- javac 0 错误（153 源文件）；**15 项审计全绿**；
- 已装 `…\mods\tianyi-1.0.11.jar`（SHA256 `1DB1A77…1F9BB`），

## 〇之一、1.0.9 的改动（相对 1.0.8）：修 mixin package


### 现象（来自 `错误报告-2026-10-24_16.25.23.zip`）

```
[Render thread/ERROR] Failed to load class net.guzhenren.tianyi.TianyiMod
org.spongepowered.asm.mixin.transformer.throwables.IllegalClassLoadError:
  net.guzhenren.tianyi.TianyiMod is in a defined mixin package
  net.guzhenren.tianyi.* owned by tianyi.mixins.json and cannot be referenced directly
[Render thread/FATAL] Failed to initialize mod containers: ERROR: failedtoloadmodclass
```

崩溃报告最后抛的是 RuOK 的
`Config 'class team.teampotato.ruok.config.RuOKConfig' has not been registered` —— 那是**假象**：
我们的模组让 FML 的容器初始化整体中止，RuOK 的配置注册（在它自己的 `@Mod` 构造里）没跑到，
而它的 TextureAtlas mixin 又先一步触发了 `RuOK.<clinit>`，于是报「配置没注册」。

### 根因

`tianyi.mixins.json` 写的是 `"package": "net.guzhenren.tianyi"`。
Mixin 的 `package` 不是「mixin 放在哪」，而是**声明一个命名空间**：
该包下的类从此只能作为 mixin 被加载，直接引用就抛 `IllegalClassLoadError`。
根包里还有 `@Mod` 主类与 94 个普通类（共 151 个），全被圈了进去 —— 模组必然加载失败。

这个错误从 1.0.0 起就存在，之前所有「javac 通过 / 13 项审计全绿」都没能发现，
因为**没有任何检查去验证 mixin 包的合法性**。

### 修法

拆成两个配置，`package` 精确到只装 mixin 的包：

| 配置 | package | mixin |
|---|---|---|
| `tianyi.open.mixins.json` | `net.guzhenren.tianyi.open.mixin` | 3 个（开窍/资质/境界） |
| `tianyi.shop.mixins.json` | `net.guzhenren.tianyi.shop.mixin` | 2 个（开石炼质/蛊方确定） |

`neoforge.mods.toml` 改成两个 `[[mixins]]`；旧 `tianyi.mixins.json` 删除。

### 新增审计 `audit_mixins.py`（这条才是真正的守门）

1. 每个 `package` 下的**所有** Java 类都必须是某个配置列出的 mixin；
2. 任何带 `@Mod` 的类不得落在 mixin 包里；
3. 配置里列的 mixin 类必须真实存在；
4. 不得残留已废弃的合并配置。

**反证**：把 `package` 改回 `net.guzhenren.tianyi` 再跑，脚本立刻红：
`有 151 个非 mixin 类会被 Mixin 拒绝直接加载` + `TianyiMod 带 @Mod 却在 mixin 包内`。
即这条审计若早存在，1.0.0 就不会发出去。
